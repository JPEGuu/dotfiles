## TDD サイクル手順

### 1. 仕様理解

- 実装対象の要件を `docs/` または会話から確認する。
- 不明点があれば実装前にユーザーに確認する。

### 2. テスト作成（RED フェーズ）

- 要件を満たすテストを先に書く。
- テストを実行して失敗することを確認する。
- 失敗しない場合、テストが正しく要件を表現できているか見直す。

### 3. 実装（GREEN フェーズ）

- テストを通過させる最小限のコードを書く。
- 過剰な設計・未来の要件への対応はしない。
- テストを実行して全て通過することを確認する。

### 4. リファクタリング（REFACTOR フェーズ）

以下の 6 項目を順番にチェックし、必要な改善を行う。

1. 命名: 変数・関数・クラス名が意図を正確に表しているか。
2. 責務: 1つの関数・クラスが1つの責務だけを持っているか。
3. 重複: DRY 原則に違反している箇所はないか。
4. 複雑度: 条件分岐・ネストが深すぎないか。
5. テスト品質: テスト自体が読みやすく、適切なケースをカバーしているか。
6. ドキュメント: 非自明なロジックにコメントが必要か。

リファクタリング後、テストが全て通過することを再確認する。

### 5. コミット

必要な場合のみ、変更のまとまりごとにステージングしてコミットする。

```bash
git add <変更ファイル>
git commit -m "test: <テスト追加の説明>"
git commit -m "feat: <実装の説明>"
```

単一コミットにまとめる場合:

```bash
git commit -m "feat: <機能名> with tests"
```
