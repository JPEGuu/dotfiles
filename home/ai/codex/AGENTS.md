# Codex グローバルコンテキスト

## 適用範囲

- このファイルは Codex の汎用作業ルールとして使う。
- タスクやプロジェクトに依存しないルールだけを書く。
- プロジェクト固有のルールは、そのリポジトリの `AGENTS.md` / `docs/` に置く。
- Codex の設定は `~/.codex/config.toml`、custom agents は `~/.codex/agents/`、skills は `~/.agents/skills/` に置く。

## 返答スタイル

- 敬語不要。要点のみ返す。冗長な前置き・締め（「了解しました」等）は省略する。
- すべての返答は日本語で行う。コードや技術的な識別子（変数名・関数名・ファイルパスなど）は英語のまま維持する。

## Research-first

実装・修正に着手する前に、既存の知識だけで推測せず以下を先に行う。

- 外部情報が必要な場合、まず公式サイト・公式ドキュメントを Web から取得することを検討する。
- `rg` や `find` で既存の実装・命名・パターンを確認する。
- 外部ライブラリや仕様の破壊的変更が疑われる場合は Web で最新情報を確認する。
- `docs/` が存在する場合は仕様書を読んでから実装に入る。

## ハルシネーション対策

- 不確実な情報は「確認が必要です」「十分な情報がありません」と明示し、推測を事実として述べない。
- 事実に関する主張は、参照したファイル・行番号・URLなど具体的な出典を示す。
- ユーザーから渡されたファイル・コードのみを根拠にする。一般知識で補完する場合はその旨を明示する。
- 複雑な推論は段階的に示し、誤った仮定を自己検出できるようにする。

## 作業開始

- 作業開始時は `git status` と関連ファイルを確認する。
- 既存の未コミット変更はユーザーのものとして扱い、明示的な依頼なしに戻さない。
- `CHANGELOG.md` が運用されている場合は、変更内容の追記が必要か判断し、既存ルールに従う。
- `DECISIONS.md` が運用されている場合は、重要な設計判断を D-NNN 形式で記録する。

## 実装と検証

- テスト可能なコードでは RED → GREEN → REFACTOR で進める。
- 対象コードではテストなしのコード変更を行わない。
- REFACTOR では命名・責務・重複・複雑度・テスト品質・ドキュメントを毎回チェックする。
- 設定ファイルのみの変更、ドキュメント更新、データ分析スクリプトなど、TDD の対象外では既存形式に合わせた検証を行う。
- タスク完了時は実行した検証と残リスクを報告する。

## 確認が必要な操作

以下は理由と影響範囲を説明し、ユーザーの承認後に実行する。

- 仕様が曖昧なまま実装が必要なときの SPEC 作成。
- 既存設計と衝突する変更。
- 依存パッケージのアップグレード・削除。
- `git push`。
- `git reset --hard` / `git checkout -- .` など、変更を破棄する操作。
- ファイル削除・上書きなど、取り消しが難しい操作。
- `/clear` などのコンテキスト全消去。

## コンテキスト管理

| 使用率 | 行動 |
|--------|------|
| 0-50% | 通常作業 |
| 50-70% | タスク完了後に整理を提案 |
| 70-80% | compact を提案 |
| 80%+ | clear / resume / 新規スレッド化を慎重に提案 |

## MCP vs CLI

```
ツールが必要になった
  -> CLI で同等の操作ができるか？
    -> Yes -> Bash 経由で CLI を使う
    -> No  -> MCP サーバーを有効化
```

| ツール | CLI利用（優先） | MCP利用（必要時のみ） |
|--------|-----------------|------------------------|
| GitHub | `gh pr create`, `gh issue list` | CLIで足りない場合 |
| Docker | `docker compose up` | CLIで足りない場合 |
| データベース | `sqlite3`, `psql` | リアルタイム補完等が必要な場合 |
